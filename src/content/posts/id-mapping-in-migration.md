[移行ツールの中身](/posts/migration-tool-internals/)では、ドメイン単位で読んで入れる骨組みを見た。
この記事はその中で**一番事故る部分**——旧システムの ID を、新システムの ID にどう対応づけるか。

## なぜ ID だけ特別扱いなのか

旧の `name` が新の `full_name` に対応する、といった列の対応表は、間違えても後から直せる。
**ID は直せない。** 理由は、ID が他のテーブルから参照されているからだ。

```text
旧 DB                              新 DB
┌────────────────┐                ┌────────────────┐
│ app_user       │                │ users          │
│  uuid = U-001  │ ←──┐           │  id = ???      │ ←──┐
└────────────────┘    │参照        └────────────────┘    │参照
┌────────────────┐    │           ┌────────────────┐    │
│ app_order      │    │           │ orders         │    │
│  user_uuid ────┼────┘           │  user_id ──────┼────┘
└────────────────┘                └────────────────┘
```

`users.id` を変えたら、`orders.user_id` に何を書くかも変わる。参照しているテーブルが 10 個あれば、
10 箇所の変換ルールが変わる。**ID の決め方が、他の全部の変換の前提になる。**

選択肢は 2 つしかない。

| 方式 | 何をするか | 向いている条件 |
| --- | --- | --- |
| **値保持** | 旧の主キーを、そのまま新の主キーとして入れる | 旧も新も UUID。1 行が 1 行のまま移る |
| **採番し直し** | 新システムで新しい ID を振る（UUID v7 など） | 旧が連番や複合キー／旧 2 行が新 1 行になる |

**既定は値保持にする。** 対応表が要らないので、子テーブルは「旧の外部キーの値をそのまま書く」だけで
済む。さらに、移行後に本番でおかしな行を見つけたとき、**同じ ID で旧 DB を引ける**。これが調査で
効く。

採番し直しが要るのは、値保持が物理的にできない所だけ。典型は**粒度が変わる**とき——旧の 2 行を
新の 1 行にまとめるなら、どちらの旧 ID を残しても嘘になる。

> ⭐ ここは「全部作り直す / 全部そのまま」で揃えなくていい。**テーブルごとに決まる**。
> 50 テーブルのうち作り直すのは 1〜2 個で、残りは値保持、という形になるのが普通。

## 作り直すなら、対応表をどこに置くか

ID を振り直したテーブルでは、**子テーブルが旧の外部キーを新 ID へ引き直す**必要がある。

```text
① 親を入れるとき            ② 子を入れるとき
   旧 S-001 を読む             旧 entry の shift_uuid = S-001
   → 新 ID 019…e7 を採番        → 対応表を引く → 019…e7
   → 対応表に記録              → shift_id に 019…e7 を書く
```

この対応表の置き場所は、プログラムのメモリではなく**新 DB の中のテーブル**にする。

```sql
CREATE TABLE _idmap_shifts (
    old_id     TEXT NOT NULL PRIMARY KEY, -- 旧の ID（文字列とは限らないので TEXT）
    new_id     UUID NOT NULL,             -- 新しく振った ID
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

DB に置く理由は 3 つある。

- **ドメインをまたぐから** — 親を入れるドメインと子を入れるドメインは別のトランザクション。
  メモリで渡そうとすると、渡すためだけの結合が生まれる
- **再実行できるから** — 「子だけ入れ直したい」とき、親を流し直さずに対応表を引ける
- **検証に使えるから** — 移行後に「対応表の行き先の数 ＝ 新テーブルの行数」を SQL で突き合わせられる

書き込みは**親テーブルへの投入と同じトランザクション**で行う。別にすると、親だけ入って対応表が
空、という状態が作れてしまう。

```go
// 親ドメインの Run の中。採番と対応表への記録を同じ tx で行う。
newID, err := uuid.NewV7() // 時刻順に並ぶ UUID。索引が効きやすい
if err != nil {
	return err
}
if err := idmap.Insert(ctx, in.TargetTx, oldID, newID.String()); err != nil {
	return err
}
```

> ⚠️ テーブルは `CREATE TABLE IF NOT EXISTS` ではなく、**`DROP` してから `CREATE`** する。
> 中身は本体テーブルと一緒に毎回入れ替わるので残す価値が無い。それより、`IF NOT EXISTS` だと
> **前回の実行で作られた古い定義が残り続ける**のが問題で、制約を変えても「既にテーブルがある環境」
> には永久に届かない。

> 💡 名前を `_` で始めておくと、業務テーブルと見分けが付く。カットオーバー後に `DROP TABLE` する
> 一時的な存在だと、名前で分かる方がいい。

## 対応表の引き方は 2 通り

子テーブル側は対応表を引いて新 ID に差し替える。素直に書くとこうなる。

```go
// 1 行につき 1 回、DB と往復する。
func Lookup(ctx context.Context, tx pgx.Tx, oldID string) (string, error) {
	const sql = "SELECT new_id::text FROM _idmap_shifts WHERE old_id = $1"
	var newID string
	err := tx.QueryRow(ctx, sql, oldID).Scan(&newID)
	return newID, err
}
```

子が数万行までなら、これで十分。ただし**数十万行になると、往復の回数が処理時間を支配する**。
親の件数が子よりずっと少ないなら、開始時に 1 度だけ全件読んで、メモリ上の `map` で引く方が速い。

```text
親 7 万件 / 子 40 万行 のとき

Lookup   → 40 万回の往復
LoadAll  → 1 回の往復で 7 万件を読んで map に載せる → 以降はメモリ上で解決
```

```go
// 開始時に 1 度だけ呼ぶ。以降はこの map から引く。
func LoadAll(ctx context.Context, q RowsQuerier) (map[string]string, error) {
	rows, err := q.Query(ctx, "SELECT old_id, new_id::text FROM _idmap_shifts")
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	out := map[string]string{}
	for rows.Next() {
		var oldID, newID string
		if err := rows.Scan(&oldID, &newID); err != nil {
			return nil, err
		}
		out[oldID] = newID
	}
	return out, rows.Err()
}
```

判断材料は 2 つだけ。**親の件数**（メモリに載るか）と、**子の件数**（往復が効いてくるか）。

> ⚠️ 引けなかったとき（対応表に無い ID を子が参照しているとき）は、**既定値を入れずにその場で
> 止める**。これは「移行対象の絞り込み」と「親の投入条件」がずれているという意味で、黙って `NULL`
> を入れると、移行が終わった後に原因を追えなくなる。

## 「1 対 1」が崩れるとき

ここが後から効いてくる。**名寄せ**——旧の 2 行が同じものを指していたので、新では 1 行にまとめる
——が入ると、対応表は**多対一**になる。

```text
旧 S-001 ─┐
          ├──> 新 019…e7   （旧 2 行 → 新 1 行）
旧 S-002 ─┘
```

影響は 3 箇所に出る。どれも「1 対 1 のつもり」で書いたコードが壊れる所だ。

| 箇所 | 1 対 1 のときの書き方 | 多対一になったら |
| --- | --- | --- |
| 制約 | `new_id` に `UNIQUE` | **外す**（張ったままだと投入時に落ちる） |
| 検証 | `COUNT(*)` と新テーブルの行数を比較 | **`COUNT(DISTINCT new_id)`** と比較する |
| 索引 | `new_id` から引かないので不要 | 検証が異なり数を数えるので**置いておく** |

そして、**どの行とどの行が同じものか**の表は、たいてい人が手で作ることになる。

```yaml
# 名前から機械的に導かない。規則が「ほぼ当たる」ことが、そのまま危険になる。
pairs:
  - old: "11111111-1111-1111-1111-111111111111"
    main: "22222222-2222-2222-2222-222222222222"
```

「名前の接頭辞を外して突き合わせる」ような規則は、34 件中 33 件は当たって 1 件外す、という挙動を
する。しかも**外した 1 件はエラーにならず、静かに間違った行き先へ入る**。だから規則ではなく表に
して、**表に載っていないものは移行前の検査で止める**。

> ⭐ 統合が入ったら、**新 ID を書く経路のすべてに `Resolve` を通す**。1 箇所でも通し忘れると、
> そこだけ統合前の ID が残り、複数列の外部キーが外れる。

```go
// まとめられる側の ID なら統合先を返し、それ以外は受け取った値をそのまま返す。
func (m *Map) Resolve(id string) string {
	if m == nil {
		return id // 表が無いときも動く（nil 安全）。呼ぶ側に分岐を作らせない
	}
	if main, ok := m.toMain[normalize(id)]; ok {
		return main
	}
	return id
}
```

## もう 1 種類のマッピング — 区分値（enum）

ID とは別に、**区分値の対応表**も要る。旧が `WaitingPayment` のような `PascalCase` の文字列、
新が `WAITING_PAYMENT` のような `UPPER_SNAKE_CASE`、という組み合わせはよくある。

ID マッピングと決定的に違うのは、**知らない値に出会ったときの扱い**だ。

```go
// マップに無い旧値はエラーにする。既定値へ寄せない。
type MissingError struct {
	EnumKey  string // どの区分値の話か（"order_status" など）
	OldValue string // 旧 DB に入っていた、知らない値
}

func (e *MissingError) Error() string {
	return fmt.Sprintf("enum %q: unknown legacy value %q", e.EnumKey, e.OldValue)
}
```

なぜ既定値に寄せてはいけないか。**本番データにしか存在しない値が、全部 1 つの区分に潰れたまま
完走する**からだ。エラーが出ないので、気づくのは業務が始まってから。しかも、どの行が潰れたのか
後から分からない。

そして、知らない値の検出は**投入を始める前に済ませる**。旧 DB の該当列を `SELECT DISTINCT` して
対応表のキーと突き合わせれば、数秒で分かる。

```sql
-- 旧 DB に実際どんな値が入っているかを数秒で出す
SELECT DISTINCT state FROM app_order;
```

500 万行を流し切った後に未知の値で中断すると、そこまでの時間がそのまま失われる。**数秒で分かる
ことを、数時間かけてから知る**のは避ける。

> 🧭 C# の `Enum.TryParse` は失敗を `bool` で返す。移行で大事なのは**その `false` を握りつぶさない**
> こと。返り値を見ずに使うと `default(T)`（＝ 先頭の値）が静かに入る。変換に失敗した 1 件は、
> 必ず「どの行か」が分かる形でログに残す。

## まとめ

- **ID の決め方が他の全部の変換の前提**になる。列の対応より先に決める
- **既定は値保持**（旧 ID をそのまま使う）。振り直すのは粒度が変わるテーブルだけに絞ると、対応表を
  持つ範囲が最小になる
- 対応表は**新 DB のテーブル**に置き、親の投入と同じトランザクションで書く。ドメインをまたいで
  使え、再実行でき、検証でも引ける
- 引き方は**親と子の件数**で決める。子が数十万行なら、1 行ごとの往復をやめて一括で読む
- 名寄せが入ると**写像は多対一**になる。`UNIQUE` を外し、検証を `COUNT(DISTINCT new_id)` に変える
- 区分値の**知らない値は既定へ寄せずに止める**。しかも投入前の検査で止める
