[移行ツールの中身](/posts/migration-tool-internals/)では、ドメイン単位で読んで投入する骨組みを見た。
この記事はその中で一番事故る部分——**旧システムの ID を、新システムの ID にどう対応づけるか**。

## 列の対応より先に、ID の扱いを決める

旧の `name` が新の `full_name` に対応する、といった列の対応表は後からでも直せる。ID は直せない。
**ID を変えると、その ID を参照している全テーブルの変換規則が変わる**からだ。

選択肢は 2 つしかない。

| 方式 | 中身 | 向いている条件 |
| --- | --- | --- |
| **値保持** | 旧の主キーをそのまま新の主キーとして入れる | 旧が UUID で、新も UUID。粒度が変わらない |
| **採番し直し** | 新システムで新しい ID を振る（UUID v7 など） | 旧が連番や複合キー、または旧 2 行が新 1 行になる |

**既定は値保持**にする。対応表が要らないので、子テーブルの変換が「旧の外部キーの値をそのまま書く」
だけで済む。移行後に本番でおかしな行を見つけたとき、旧 DB の同じ ID を引ける利点も大きい。

採番し直しが要るのは、値保持ができない所だけ。典型は**粒度が変わる**とき——旧テーブルの 2 行を
新テーブルの 1 行にまとめるなら、どちらの旧 ID を残しても嘘になる。

> ⭐ ここは「全部作り直す / 全部そのまま」で揃えなくていい。**テーブルごとに決まる**。作り直すのは
> 必要な 1〜2 テーブルだけ、残りは値保持、という形になるのが普通。

## 作り直すなら、対応表をどこに置くか

採番し直したテーブルでは、子テーブルが旧の外部キーを新 ID へ引き直す必要がある。その対応表の
置き場所は、プロセスのメモリではなく**投入先 DB のテーブル**にする。

```sql
CREATE TABLE _idmap_shifts (
    old_id     TEXT NOT NULL PRIMARY KEY,
    new_id     UUID NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

DB に置く理由は 3 つ。

- **ドメインをまたぐ**: 親を入れるドメインと、子を入れるドメインは別のトランザクション。メモリだと
  受け渡しのための結合が生まれる
- **再実行できる**: 子だけやり直したいとき、親を流し直さずに対応表を引ける
- **検証に使える**: 移行後に「対応表の行き先の数 = 新テーブルの行数」を SQL で突き合わせられる

書き込みは**親テーブルへの投入と同じトランザクション**で行う。別にすると、親だけ入って対応表が
空、という状態が作れてしまう。

```go
// 親ドメインの Run の中。採番と対応表への記録を同じ tx で行う。
newID, err := uuid.NewV7()
if err != nil {
	return err
}
if err := idmap.Insert(ctx, in.TargetTx, oldID, newID.String()); err != nil {
	return err
}
```

> ⚠️ テーブルは `CREATE TABLE IF NOT EXISTS` ではなく **`DROP` してから `CREATE`** する。中身は本体
> テーブルと一緒に毎回入れ替わるので残す価値が無く、`IF NOT EXISTS` だと**前回の実行で作られた
> 古い定義が残り続ける**。制約を変えても既にテーブルを持っている環境には届かない。

> 💡 接頭辞 `_` を付けて、業務テーブルと見分けが付くようにしておく。カットオーバー後に
> `DROP TABLE` する一時的な存在だと、名前で分かる方がいい。

## 引き方は 2 通り — 1 件ずつか、まとめてか

子テーブル側は対応表を引いて新 ID に差し替える。素直に書くとこうなる。

```go
// 1 行につき 1 往復。
func Lookup(ctx context.Context, tx pgx.Tx, oldID string) (string, error) {
	const sql = "SELECT new_id::text FROM _idmap_shifts WHERE old_id = $1"
	var newID string
	err := tx.QueryRow(ctx, sql, oldID).Scan(&newID)
	return newID, err
}
```

子が数万行までならこれで足りる。**数十万行になると、往復回数が処理時間を支配する**。親の件数が
子よりずっと少ないなら、開始時に 1 度だけ全件読んでメモリの map で解決する方が速い。

```go
// 開始時に 1 度だけ。以降はメモリ上で引く。
func LoadAll(ctx context.Context, q RowsQuerier) (map[string]string, error) {
	rows, err := q.Query(ctx, "SELECT old_id, new_id::text FROM _idmap_shifts")
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	out := map[string]string{}
	for rows.Next() {
		var oldID, newID string
		if err := rows.Scan(&oldID, &newID); err != nil {
			return nil, err
		}
		out[oldID] = newID
	}
	return out, rows.Err()
}
```

判断材料は**親の件数**（メモリに載るか）と**子の件数**（往復が効くか）。親 7 万件・子 40 万行なら、
40 万回の往復より 7 万件の一括読み込みが明らかに安い。

> ⚠️ 引けなかったときは **既定値に寄せず、その場で止める**。対応表に無い親を参照している子は、
> 移行対象の絞り込みと親の投入条件がずれているという意味で、黙って `NULL` を入れると移行後に
> 原因を追えなくなる。

## 写像は 1 対 1 とは限らない

ここが後から効いてくる。**名寄せ**——旧の 2 行を新の 1 行にまとめる——が入ると、対応表の写像は
多対一になる。

```sql
-- 旧 2 行が同じ new_id を指す。だから new_id に UNIQUE を張れない。
old_id = 'shift-a-2026-01-05' → new_id = '019...e7'
old_id = 'shift-b-2026-01-05' → new_id = '019...e7'
```

影響は 3 箇所に出る。

- **制約**: `new_id` の UNIQUE を外す。張ったまま名寄せを足すと投入時に落ちる
- **検証**: 新テーブルの行数と突き合わせるのは `COUNT(*)` ではなく
  `COUNT(DISTINCT new_id)`。ここを直し忘れると、名寄せした分だけ件数が合わずに警告が出続ける
- **索引**: `new_id` から引く経路が無くても、検証が異なり数を数えるので索引は置いておく

名寄せの対応表そのもの（どの行とどの行が同一人物か）は、たいてい**人が作る**ことになる。

```yaml
# 名前から機械的に導かない。規則が「ほぼ当たる」ことがそのまま危険になる。
pairs:
  - old: "11111111-1111-1111-1111-111111111111"
    main: "22222222-2222-2222-2222-222222222222"
```

名前の接頭辞を外して突き合わせる、のような規則は 34 件中 33 件当たって 1 件外す、という挙動をする。
外した 1 件は**エラーにならず静かに間違った行き先へ入る**ので、規則ではなく表にして、
**表に載っていないものは事前検査で止める**のが安全側になる。

> ⭐ 統合が入ったら、**新 ID を書く経路すべてに `Resolve` を通す**。1 箇所でも通し忘れると、そこだけ
> 統合前の ID が残り、複合外部キーが外れる。

```go
// サブ側なら統合先を返し、それ以外は受け取った値をそのまま返す。
func (m *Map) Resolve(id string) string {
	if m == nil {
		return id // nil 安全にして、呼ぶ側に分岐を作らせない
	}
	if main, ok := m.toMain[normalize(id)]; ok {
		return main
	}
	return id
}
```

## もう一種類のマッピング — 区分値

ID とは別に、**区分値（enum）の対応表**も要る。旧が Java の `@Enumerated(STRING)` なら
`PascalCase` の文字列、新が `UPPER_SNAKE_CASE` の `CHECK` 制約、というのはよくある組み合わせだ。

ID マッピングと違うのは、**未知の値に出会ったときの扱い**。

```go
// マップに無い旧値はエラーにする。既定値へ寄せない。
type MissingError struct {
	EnumKey  string
	OldValue string
}

func (e *MissingError) Error() string {
	return fmt.Sprintf("enum %q: unknown legacy value %q", e.EnumKey, e.OldValue)
}
```

既定値に寄せると、**本番データにしか存在しない値が全部 1 つの区分に潰れて完走する**。エラーが
出ないので、気づくのは業務が始まってからになる。

そして未知値の検出は、**投入を始める前に済ませる**。旧 DB の該当列を `SELECT DISTINCT` して
マップのキーと突き合わせれば、数秒で分かる。500 万行を流し切った後に未知値で中断するのは、
やり直しの時間がそのまま失われる。

> 🧭 C# の `Enum.TryParse` は既定で大文字小文字を区別し、失敗を `bool` で返す。移行では
> **`false` を握りつぶさない**のが要点で、返り値を捨てた瞬間に `default(T)` = 先頭の値が入る。
> 「変換に失敗した 1 件」は必ず行の識別子付きで記録する。

## まとめ

- **既定は値保持**（旧 ID をそのまま使う）。採番し直すのは粒度が変わるテーブルだけに絞ると、
  対応表を持つ範囲が最小になる
- 対応表は**投入先 DB のテーブル**に置く。ドメインをまたいで使え、再実行でき、検証でも引ける
- 引き方は**親と子の件数**で決める。子が数十万行なら 1 件ずつの往復をやめて一括で読む
- 名寄せが入ると**写像は多対一**になる。`UNIQUE` を外し、検証は `COUNT(DISTINCT new_id)` に変える
- 区分値の未知値は**既定へ寄せずに止める**。しかも投入前の事前検査で止める
