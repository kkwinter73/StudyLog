lint（静的解析）は、コードを**実行せずに**怪しい書き方を指摘する仕組みだ。うまく入れると
レビューが軽くなり、下手に入れると「CI を通すための無意味な修正」が増える。この記事では
Go の lint が何を見ているのか、導入のメリットとデメリット、そして例外を明示する
`//nolint` の使い方とトレードオフを押さえる。

品質を後付けせず作り込むという[QA の考え方](/posts/qa-quality-built-in/)の、一番安く効く入口が lint だ。

## lint は何を見ているのか

Go には段階の違う2つの道具がある。

| 道具 | 立ち位置 | 見るもの |
| --- | --- | --- |
| `gofmt` | 標準・整形 | 書式。議論の余地がないので**常に全適用** |
| `go vet` | 標準・同梱 | 「ほぼ確実に間違い」だけ。誤検知が極めて少ない |
| `golangci-lint` | サードパーティ | 複数リンターの束。方針の問題まで踏み込む |

`go vet` が拾うのは、コンパイルは通るが意図と食い違う類だ。

```go
name := "gopher"
fmt.Printf("hello %d\n", name) // vet: arg name for %d verb
```

`golangci-lint` はこの上に、戻り値の `error` を捨てていないか（`errcheck`）、
使われない変数（`unused`）、より簡潔に書ける箇所（`staticcheck`）などを重ねる。
設定は `.golangci.yml` に置く。

```yaml
version: "2"
linters:
  default: standard      # errcheck, govet, ineffassign, staticcheck, unused
  enable:
    - revive             # 命名やスタイルの指摘を追加
  exclusions:
    rules:
      - path: _test\.go
        linters: [errcheck]
```

> 🧭 C# なら `gofmt` ≒ `dotnet format`、`go vet` ≒ コンパイラ警告、`golangci-lint` ≒ Roslyn Analyzers + StyleCop。CI で lint を失敗扱いにするのは `TreatWarningsAsErrors` と同じ発想。

## メリット — 人が見なくていいものを減らす

lint の価値は「バグが見つかる」ことよりも、**レビューの議題からノイズが消える**ことにある。

- **指摘が人ではなく機械から来る**。命名や書式の話でレビューが往復しない。感情も乗らない
- **本当に危ない型のバグを拾う**。`err` の捨て忘れ、`defer` の中の誤り、`Printf` の型不一致は
  レビューでは見落とすが lint は必ず気づく
- **コードベースが均質になる**。他人のコードを読む速度が上がり、差分レビューも読みやすい
- **入るのが早い**。CI で数十秒。[テスト](/posts/testing-strategy-pyramid/)より前に落ちるので手戻りが小さい

> 💡 特に効くのが `errcheck`。Go は例外がなく `error` を戻り値で返すので、**受け取り忘れが
> 静かに動くバグになる**。[エラーをラップして返す](/posts/error-handling-wrapping/)規約と
> セットで入れると効果が大きい。

## デメリット — 偽陽性と「通すための変更」

一方でコストは確実にある。ここを見ずに `default: all` にすると必ず荒れる。

| コスト | 具体的に起きること |
| --- | --- |
| 偽陽性 | 意図してやっている書き方まで怒られる。無視が習慣になると全指摘が無視される |
| 通すための変形 | 指摘を消すために**読みにくいコードに書き換える**。品質は下がるのに CI は緑 |
| ルールの政治 | 「この指摘は必要か」の議論が増える。技術ではなく好みの話になりがち |
| CI 時間と不安定さ | リンター追加でビルドが伸びる。バージョン上げで**昨日通ったコードが落ちる** |

一番たちが悪いのは2番目だ。たとえば `errcheck` を黙らせるために `_ = doSomething()` と
書くのは、**エラーを見ていないという事実を隠しただけ**で何も改善していない。

> ⚠️ リンターのバージョンは CI で**固定する**。`latest` にすると、自分のコードを変えていないのに
> ある日突然 CI が赤くなる。原因調査が本来の作業を止める。

## //nolint — 例外を明示する

どんなルールにも正当な例外はある。Go では `//nolint` コメントでその箇所だけ抑制できる。

```go
// 行単位（その行だけ）
_, _ = io.Copy(io.Discard, resp.Body) //nolint:errcheck // 読み捨て。失敗しても後続に影響しない

//nolint:gosec // 固定の内部パスのみ。ユーザー入力は通らない
data, err := os.ReadFile(configPath)
```

書き方には決まりがある。

- **`//nolint` の前にスペースを入れない**（`// nolint` は機械可読コメントとして扱われない）
- **抑制するリンター名を必ず書く**。`//nolint` だけだと**その行の全リンターが黙る**
- **`//` に続けて理由を書く**。「なぜ例外なのか」が半年後の自分とレビュアーへの説明になる

置く場所でスコープが変わる。

| 置き場所 | 効く範囲 |
| --- | --- |
| 文の行末 | その行だけ |
| 宣言の直前の行に単独で | その関数・型・変数の宣言全体 |
| `package` 宣言の前 | ファイル全体（広すぎるので基本使わない） |

そして `nolint` 自体を lint できる。`nolintlint` を有効にすると「理由が書かれていない
`nolint`」「もう不要になった `nolint`」を指摘してくれる。

```yaml
linters:
  enable:
    - nolintlint
  settings:
    nolintlint:
      require-explanation: true   # 理由なしを禁止
      require-specific: true      # リンター名なしを禁止
      allow-unused: false         # 使われていない nolint を指摘
```

> ⭐ **理由付きの `nolint` は負債ではなく設計判断の記録**。逆に理由のない `nolint` は
> 「怒られたので黙らせた」以上の情報がなく、消していいかも判断できない。

> 🧭 C# の `#pragma warning disable CS0168` や `[SuppressMessage(..., Justification = "...")]` と同じ役割。Justification を書く習慣がそのまま `//nolint:xxx // 理由` に対応する。

## 抑制の4段階 — どこで例外を認めるか

`nolint` は選択肢のひとつでしかない。**例外の広さと合わせる**のがトレードオフの本質だ。

| 手段 | 効く範囲 | 向いている場面 |
| --- | --- | --- |
| コードを直す | 恒久 | 大半。まずこれを検討する |
| `//nolint:xxx` | その行・その宣言 | 局所的で、理由が1行で説明できる例外 |
| 設定の `exclusions` | パス単位（生成コード、`_test.go`） | 構造的にルールが合わない領域 |
| リンターを無効化 | プロジェクト全体 | そのルールがチームの方針と合わない |

判断の順番は上から下。**「この例外は本当にこの行だけの話か？」**を毎回問う。同じ `nolint` が
10箇所に増えたら、それは行単位の例外ではなく**設定で扱うべきルール**だというサインだ。

> 💡 逆に、設定でリンターを丸ごと切ると「なぜ切ったか」がコードから見えなくなる。
> `.golangci.yml` にもコメントで理由を残す。判断の記録という点では `nolint` と同じ扱い。

## 既存コードに後から入れるとき

新規プロジェクトなら最初から厳しくできる。問題は**既存コードに後入れするとき**で、
素直に有効化すると数千件出て手が止まる。

```bash
# 差分だけを見る（既存の指摘は無視して、新しく書いた行だけ落とす）
golangci-lint run --new-from-rev=origin/main
```

これで「これから書くコードは綺麗、既存は触るときに直す」という現実的な運用になる。
既存分をまとめて直したくなっても、**大量の機械的な修正はレビューできない**ので
リンター1つずつ・小さい PR に割るほうが安全だ。

段階の付け方の目安。

1. `gofmt` + `go vet` を CI で必須にする（誤検知がなく、反対しにくい）
2. `errcheck` / `staticcheck` / `unused` を足す。ここまでで実害のある指摘は概ね拾える
3. スタイル系（`revive` など）は**チームで合意してから**。合意なしに入れると政治になる
4. `nolintlint` を入れて、例外に理由を強制する

[CI に組み込む](/posts/cicd-github-actions/)ときは、キャッシュを効かせて実行時間を短く保つ。
lint が遅いと「ローカルで走らせない」が定着し、CI で初めて落ちるようになる。

## まとめ

- lint の主な価値はバグ検出よりも**レビューの議題からノイズを消すこと**
- コストは偽陽性と「**通すためだけの書き換え**」。後者は品質を下げるのに CI は緑になる
- `//nolint:リンター名 // 理由` で局所的に抑制する。スペースなし・名前あり・理由ありが必須
- 抑制は **直す → `nolint` → パス除外 → 無効化** の順に検討し、例外の広さを揃える
- 既存コードには `--new-from-rev` で差分から。厳しさは段階的に、スタイル系は合意してから
- リンターのバージョンは固定する。`latest` は無関係な赤 CI を生む

## 次にやること

- `go vet ./...` を CI に入れ、次に `errcheck` を足して既存コードの指摘数を数えてみる
- 出た指摘のうち「直す」「`nolint` で理由付き例外」「除外」に自分で振り分けてみる
- `nolintlint` を有効にして、既存の `nolint` に理由が書かれているか確認する
